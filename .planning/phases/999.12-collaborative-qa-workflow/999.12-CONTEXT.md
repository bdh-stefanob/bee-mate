# Phase 999.12: Collaborative QA Workflow — Context

**Gathered:** 2026-06-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Allow QA colleagues to contribute to the step catalog directly from the app without touching the `main` branch. Three connected sub-features:

1. **Branch selector** — app commits/pushes proposals to a dedicated `catalog` branch (configurable). The `catalog` branch is permanent and parallel to `main` — never merged back. `main` holds app code and scaffold; `catalog` holds the evolving step catalog and proposals.

2. **Per-user commit identity** — each colleague configures `commitName`, `commitEmail`, and `githubToken` (PAT) in Settings as a one-time setup. Before every push the app shows a "Committing as: Name <email> → branch: catalog" preview with confirm/cancel.

3. **Step proposal flow** — unknown step detected inline in CodeMirror → colleague clicks indicator → modal pre-fills expression + auto-detected keyword → colleague picks area → confirms → step is pushed to `step-proposals.json` on `catalog` branch. Proposals are shown in Catalog and StepBrowser with a distinct "Proposed" badge.

**Guiding constraint:** QA colleague operational burden must be minimal. Configuration is one-time (Settings). Daily workflow (write feature → propose step → push) requires no manual Git operations.

**OUT OF SCOPE:**
- GitHub OAuth app (PAT only for now)
- In-app review/approval UI (review happens on GitHub by browsing the catalog branch)
- Merging catalog→main (permanent parallel branches)
- Mobile responsiveness

</domain>

<decisions>
## Implementation Decisions

### Branch Lifecycle

- **D-01:** A new Settings field `catalogBranch` (default: `catalog`) configures the proposals branch. Separate from the existing `githubBranch` field (used for feature file pushes, default `main`).
- **D-02:** If the `catalogBranch` doesn't exist on the remote, the app auto-creates it from `main` via GitHub API on first push. No manual maintainer action required.
- **D-03:** The `catalog` branch is shared by all QA colleagues (no per-user branches).
- **D-04:** Conflict strategy: optimistic fetch-merge-push. Before writing `step-proposals.json`, the app fetches the current file from the `catalog` branch (getting the fresh SHA), adds the new entry in memory, then pushes. If the same expression already exists, it shows an explicit duplicate error. This is the same pattern already used by `/api/github/push` for feature files.

### Catalog Source of Truth

- **D-05:** When `githubToken` + `catalogBranch` are configured, the app reads `step-catalog.json` and `step-proposals.json` from the GitHub API (`catalog` branch) on load — not from the local filesystem. This ensures all colleagues always see the same current state regardless of which local branch they have checked out.
- **D-06:** Fallback: if GitHub credentials are not configured (or the API call fails), the app falls back to reading catalog files from the local workspace filesystem (existing behavior). No blocking error.

### Per-User Commit Identity

- **D-07:** Two new Settings fields: `commitName` (display name for Git commits) and `commitEmail`. These are separate from `githubToken` (which authenticates the API call). The PAT authenticates; name + email appear as the commit author.
- **D-08:** A "Committing as: Name \<email\> → branch: catalog" preview is shown always before every push (feature file or step proposal), not only when data is missing. The colleague confirms or cancels. Ensures no accidental commits with wrong identity.
- **D-09:** Settings page includes documentation on how to obtain a GitHub PAT (link + scopes required: `repo`, `contents:write`).

### Step Proposal UX

- **D-10:** Detection: lines with step expressions not found in the combined catalog (step-catalog.json + step-proposals.json) are highlighted inline in CodeMirror (underline or color). Non-blocking — does not interrupt writing.
- **D-11:** The colleague clicks the inline indicator (or a trigger on hover). A modal opens — same visual pattern as the Step Detail modal (already built).
- **D-12:** Modal pre-fills: expression (from the editor line), keyword (auto-detected from Given/When/Then prefix). Colleague selects `area` from a dropdown listing existing areas in the catalog. Minimum friction.
- **D-13:** Proposals are stored in `step-proposals.json` (a separate file from `step-catalog.json`) on the `catalog` branch. Schema mirrors `step-catalog.json` entries with `status: "proposed"` and `sourceRef` set to the proposer's `commitName`.
- **D-14:** Both `step-catalog.json` and `step-proposals.json` are loaded and shown together in the Catalog page and StepBrowser. Proposals show a distinct visual badge ("Proposed") to distinguish them from official catalog entries (`wanted`, `implemented`).

### Review and Merge Flow

- **D-15:** Maintainer reviews proposals by browsing the `catalog` branch on GitHub (no in-app review page). Proposals are visible in the `step-proposals.json` diff.
- **D-16:** When a developer implements a proposed step (on `main`), they manually move the entry from `step-proposals.json` (catalog branch) to `step-catalog.json` with `status: "implemented"`. No automated promotion.
- **D-17:** No catalog→main merge workflow. The `catalog` branch accumulates step knowledge indefinitely and receives only new entries or status updates to existing ones.

### Claude's Discretion

- Exact highlight style for unknown steps in CodeMirror (underline color, squiggly, or left-border gutter icon)
- Debounce/timing for the catalog load from GitHub API on app startup
- Exact PAT scope documentation copy in Settings
- Error message wording for duplicate proposal detection

</decisions>

<specifics>
## Specific Ideas

- **step-proposals.json schema:** same as step-catalog.json entries, with `status: "proposed"` and `sourceRef: "{commitName}"`. Example:
  ```json
  {
    "expression": "the user verifies their age",
    "keyword": "When",
    "app": "brochure-clinic",
    "area": "registration",
    "status": "proposed",
    "sourceRef": "Mario Rossi",
    "proposedAt": "2026-06-24T10:00:00Z"
  }
  ```
- **Branch auto-create via GitHub API:** `GET /repos/{owner}/{repo}/git/ref/heads/{catalogBranch}` — if 404, `POST /repos/{owner}/{repo}/git/refs` with `ref: "refs/heads/{catalogBranch}"` and `sha` from main branch HEAD.
- **Commit author in GitHub API:** The GitHub REST API `PUT /contents` accepts `committer` and `author` objects: `{ "name": commitName, "email": commitEmail }`. This sets the Git commit author.
- **Catalog load on startup:** `GET /repos/{owner}/{repo}/contents/step-catalog.json?ref={catalogBranch}` — response has `content` (base64). Same for step-proposals.json (treat 404 as empty array).
- **Guiding principle quote (from user):** "L'operatività del collega QA che utilizza l'app deve essere minimale" — minimum friction for daily use; one-time Settings setup.

</specifics>

<deferred>
## Deferred Ideas

- GitHub OAuth app (browser-based auth instead of PAT) — reduces setup friction further but adds OAuth infrastructure
- In-app proposal review UI (Approve/Reject buttons for maintainer) — currently done on GitHub
- Automated promotion of implemented proposals (status update from proposed → implemented) — manual for now
- Per-user branches (`catalog/mario`, `catalog/giulia`) — explicit decision against this; shared branch chosen
- Pull catalog updates via webhook or polling — all sync is currently pull-on-load only

</deferred>
