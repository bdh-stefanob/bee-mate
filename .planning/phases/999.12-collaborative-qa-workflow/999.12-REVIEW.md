## Summary

Reviewed the full collaborative-QA-workflow feature set: GitHub integration utilities,
the catalog/propose API routes, the GherkinEditor with click-to-propose, the
CommitPreviewDialog and ProposeStepModal, the StepBrowser and StepCatalog, settings
persistence, and all associated tests.

The overall architecture is clean and the threat-mitigation work (token sanitization,
GITHUB_NAME_RE validation, `<>` stripping from commit identity) is correctly applied.
The main concerns are:

- One unchecked HTTP response in `branchEnsure` that will produce a misleading
  runtime crash instead of a proper error.
- A catalog-match regex escape with duplicate character-class entries that may
  silently misclassify steps.
- A GitHub-headers omission in the post-proposal catalog refresh that causes
  the orange underline to persist even after a step is successfully proposed.
- `GITHUB_NAME_RE` is copy-pasted into `github/push/route.ts` instead of
  being imported from `github-utils.ts`.
- The Escape-key listener in `StepDetailModal` is always registered, not gated

## Critical Issues

### CR-01: `branchEnsure` does not validate the base-branch GET response

**File:** `web-ui/src/lib/github-utils.ts:133-135`

**Issue:** After the catalog branch is confirmed to be missing (404), the code fetches
the base branch HEAD to obtain its SHA. The response is consumed unconditionally:

```ts
const baseRes = await fetch(baseUrl, { headers: ghHeaders(token) });
const baseJson = (await baseRes.json()) as { object: { sha: string } };
const baseSha = baseJson.object.sha;
```

If the base branch fetch returns a non-2xx (e.g. 403 Forbidden, 404 if the base branch
does not exist, or a network error), `baseJson.object` will be `undefined` and the
line `baseJson.object.sha` will throw `TypeError: Cannot read properties of undefined
(reading 'sha')`. This obscures the real error (the response status) and makes
debugging very hard.

**Fix:**
```ts
const baseRes = await fetch(baseUrl, { headers: ghHeaders(token) });
if (!baseRes.ok) {
  throw new Error(`GitHub GET failed: ${baseRes.status}`);
}
const baseJson = (await baseRes.json()) as { object: { sha: string } };
const baseSha = baseJson.object.sha;
```

### CR-02: Catalog-match regex escape has duplicate character-class entry

**File:** `web-ui/src/lib/catalog-match.ts:13`

**Issue:** The character set passed to `replace(/[.*+?^$|[\]\\()[\]{}]/g, '\\$&')` contains
the sequence `[\]` twice:

```ts
const pattern = segments.map(s => s.replace(/[.*+?^$|[\]\\()[\]{}]/g, '\\$&')).join('.+');
```

The first `[\]` inside the character class closes it prematurely (the parser sees `[`,
then `.`, `*`, `+`, `?`, `^`, `$`, `|`, `[`, `\]` which ends the class, then the
remainder `\\()[\]{}]` is treated as literal characters outside the class). This means
characters like `(`, `)` and the second `[`, `{`, `}` are NOT escaped.

A step expression containing a literal `(` — which is common in BDD (e.g. "the user
selects an option (optional)") — will produce an invalid or mis-anchored regex. The
`try/catch` in `matchesCatalog` will silently return `false`, causing the step to be
permanently shown as "unknown" even when it exists in the catalog.

**Fix:**
```ts
// Use the well-known escapeRegExp pattern:
const escapeRegExp = (s: string) => s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');

export function matchesCatalog(stepText: string, expressions: string[]): boolean {
  return expressions.some(expr => {
    const segments = expr.split(/\{[^}]+\}/);
    const pattern = segments.map(escapeRegExp).join('.+');
    try { return new RegExp(`^${pattern}$`, 'i').test(stepText); }
    catch { return false; }
  });
}
```

## Warnings

### WR-01: Post-proposal catalog refresh omits GitHub headers

**File:** `web-ui/src/app/editor/_content.tsx:406` and `:451`

**Issue:** After `doPropose` and `doProposeSingle` successfully push a new step to the
catalog branch on GitHub, they refresh the local step-expressions list with:

```ts
const catalogRes = await fetch('/api/catalog');
```

No GitHub headers are passed. This always hits the FS fallback in the API route,
returning the local `step-catalog.json` which does not include proposals. The newly
proposed step is absent from `stepExpressions`, so the orange underline in the editor
persists after the proposal succeeds — misleading the user into thinking the proposal
failed.

**Fix:** Pass the same GitHub headers as the proposal request:
```ts
const catalogRes = await fetch('/api/catalog', {
  headers: {
    'x-github-token': settings.githubToken,
    'x-github-owner': settings.githubOwner,
    'x-github-repo': settings.githubRepo,
    'x-catalog-branch': settings.catalogBranch || 'catalog',
  },
});
```
Apply the same fix at both lines 406 and 451.

### WR-02: `GITHUB_NAME_RE` duplicated in `github/push/route.ts` instead of imported

**File:** `web-ui/src/app/api/github/push/route.ts:49`

**Issue:** The route defines its own local copy of the validation regex:

```ts
const GITHUB_NAME_RE = /^[a-zA-Z0-9_.\-]+$/;
```

This is identical to the exported `GITHUB_NAME_RE` in `github-utils.ts`, but it is not
imported from there. If the shared regex is tightened in the future (e.g. to block
additional characters), the push route will silently keep the old, permissive rule,
creating a security regression.

**Fix:**
```ts
// github/push/route.ts — remove local definition and add import:
import { GITHUB_NAME_RE, sanitizeError } from '@/lib/github-utils';
```
Then delete line 49 of `route.ts`.

### WR-03: `StepDetailModal` Escape-key listener registered unconditionally

**File:** `web-ui/src/components/StepDetailModal.tsx:37-41`

**Issue:** The keydown listener is registered without gating on whether the modal is
open:

```ts
useEffect(() => {
  const handler = (e: KeyboardEvent) => { if (e.key === 'Escape') onClose(); };
  window.addEventListener('keydown', handler);
  return () => window.removeEventListener('keydown', handler);
}, [onClose]);
```

`StepDetailModal` is rendered at the top of `StepCatalog` as
`<StepDetailModal step={selectedStep} onClose={...} />`. When `selectedStep` is null
the component returns `null` early in the render, but the `useEffect` runs before the
early return. Every Escape keypress — even when no modal is visible — calls `onClose`,
which calls `setSelectedStep(null)` in the parent. Compare to `CommitPreviewDialog` and
`ProposeStepModal` which correctly gate their listener on `open`:

```ts
// Correct pattern (from CommitPreviewDialog.tsx:44-51):
useEffect(() => {
  if (!open) return;
  ...
}, [open, onCancel]);
```

**Fix:**
```ts
useEffect(() => {
  if (!step) return;    // gate on visibility, not just render
  const handler = (e: KeyboardEvent) => { if (e.key === 'Escape') onClose(); };
  window.addEventListener('keydown', handler);
  return () => window.removeEventListener('keydown', handler);
}, [step, onClose]);
```

### WR-04: `keyword` field accepted without runtime validation, cast to union type

**File:** `web-ui/src/app/api/catalog/propose/route.ts:56` and `:153`

**Issue:** The `keyword` field arriving from the request body is cast directly to the
union type without any runtime check:

```ts
...(keyword ? { keyword: keyword as CatalogStep['keyword'] } : {}),
```

TypeScript erases types at runtime. If a client sends `keyword: "GIVEN"` or
`keyword: "click"`, the value is stored verbatim in `step-proposals.json` and
`step-catalog.json`, violating the `'Given' | 'When' | 'Then'` contract expected by
downstream consumers. The FS path (`proposeToFs`, line 56) and the GitHub path (line
153) both have this issue.

**Fix:**
```ts
const VALID_KEYWORDS = new Set(['Given', 'When', 'Then']);
const safeKeyword = VALID_KEYWORDS.has(keyword ?? '') ? keyword : undefined;
// then use safeKeyword in the spread
...(safeKeyword ? { keyword: safeKeyword as CatalogStep['keyword'] } : {}),
```

### WR-05: GitHub PAT stored in `localStorage` without any user warning

**File:** `web-ui/src/hooks/useSettings.ts:60` and `web-ui/src/app/settings/page.tsx`

**Issue:** The GitHub Personal Access Token is persisted to `localStorage` like all
other settings:

```ts
localStorage.setItem(STORAGE_KEY, JSON.stringify(next));
```

`localStorage` is accessible to any JavaScript executing on the same origin. While this
is a common pattern for client-side tooling, there is no warning to the user about the
risk. The settings page's password-type input (`type: 'password'`) masks the value
visually but provides no storage security.

**Fix:** Add a visible security notice to the settings page near the token field:

```tsx
{field('githubToken', t.settings.githubToken, t.settings.githubTokenHint, 'password')}
<p className="text-xs text-amber-600 dark:text-amber-400">
  Token stored in browser localStorage. Use a fine-grained PAT with minimal
  scopes (contents: write on this repo only).
</p>
```

Consider using `sessionStorage` over `localStorage` so the token does not persist
across browser sessions.

### IN-03: IIFE inside JSX prop in `_content.tsx`

**File:** `web-ui/src/app/editor/_content.tsx:668`

**Issue:** The `app` prop of `<ProposeStepModal>` is computed via an inline IIFE:

```tsx
app={(() => { const tagLine = content.match(/.../)...; return ...; })()}
```

This is evaluated on every render pass, is hard to read, and makes the prop difficult
to extract or test independently.

**Fix:** Hoist to a variable or `useMemo` near the `unknownSteps` memo (the same
tag-extraction logic is already used elsewhere in the component):

```ts
const currentApp = useMemo(() => {
  const tagLine = content.match(/^(@\S+(?:\s+@\S+)*)/m);
  const tags = tagLine?.[1].match(/@(\S+)/g)?.map(tag => tag.slice(1)) ?? [];

}, [content]);
```
