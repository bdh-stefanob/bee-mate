<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/catalog/propose | token, owner, repo, catalogBranch, commitName, commitEmail cross via headers |
| client → /api/github/push | commitName/commitEmail added to existing token/owner/repo/branch headers |
| API routes → GitHub API | branch + identity interpolated into URLs / commit author fields |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-999.12-05 | Tampering/Injection | catalogBranch in propose route GitHub URL | mitigate | Validate `branch` (and owner/repo) with `GITHUB_NAME_RE` before any fetch; 400 on invalid |
| T-999.12-06 | Tampering/Header injection | commitName/commitEmail flow into commit metadata | mitigate | Strip `<>` from commitName, cap commitName ≤100 chars, commitEmail ≤200 chars before use |
| T-999.12-07 | Information Disclosure | token in propose/push error responses | mitigate | Wrap returned error with `sanitizeError(message, token)`; token read from header only, never body |
| T-999.12-08 | Spoofing | colleague could push with arbitrary commitName | accept | Identity is self-declared by design (D-07); PAT still authenticates the API call; shared private team repo |
| T-999.12-09 | Tampering | concurrent proposal PUT with stale SHA (race) | accept | Optimistic concurrency; GitHub rejects stale SHA, user retries; explicit error surfaced |
</threat_model>
