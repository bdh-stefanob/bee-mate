## Summary

Phase 999.12 adds three connected capabilities to the existing Next.js web-ui: branch-scoped catalog reads, per-user commit identity, and a step-proposal flow. The codebase already has ~80% of the required infrastructure:

- **`/api/github/push`** already implements the fetch-SHA → PUT pattern (D-04 pattern) for feature files. The same logic needs to be extracted into a shared utility and reused for `step-proposals.json`.
- **`_content.tsx`** already computes `unknownSteps` (with keyword and page inference) and has a proposal panel with `handlePropose` that calls `/api/catalog/propose`. This existing flow currently writes to the local `step-catalog.json`. Phase 999.12 replaces it: proposals now go to GitHub (catalog branch) via a new/updated `/api/catalog/propose` route.
- **`GherkinEditor`** uses CodeMirror 6 with `@codemirror/view` 6.43.1, which ships `Decoration` and `ViewPlugin`. Unknown-step highlighting requires a new `ViewPlugin` extension — the `gherkinLinter` (already using `@codemirror/lint`) demonstrates the pattern of iterating lines in a CodeMirror 6 extension.
- **`useSettings`** and the Settings page are straightforward to extend with three new fields; the save-on-blur pattern is already established.

**Primary recommendation:** Build in three sequential waves: (1) Settings + catalog branch read, (2) GitHub push infrastructure + commit-identity preview, (3) inline highlighting + proposal modal.

### Pattern 1: GitHub API Fetch-SHA + PUT (existing, extend)

The pattern already exists in `/api/github/push/route.ts`. Extract into `lib/github-utils.ts`:

```typescript
// Source: web-ui/src/app/api/github/push/route.ts (existing, verified)
async function getFileSHA(
  owner: string, repo: string, filePath: string, branch: string, token: string
): Promise<string | undefined> {
  const url = `https://api.github.com/repos/${owner}/${repo}/contents/${filePath}?ref=${branch}`;
  const res = await fetch(url, { headers: ghHeaders(token) });
  if (res.ok) return ((await res.json()) as { sha: string }).sha;
  if (res.status === 404) return undefined; // file does not exist yet
  throw new Error(`GitHub GET failed: ${res.status}`);
}

async function putContents(
  owner: string, repo: string, filePath: string, branch: string, token: string,
  content: string, sha: string | undefined,
  message: string, author?: { name: string; email: string }
): Promise<void> {
  const body: Record<string, unknown> = {
    message,
    content: Buffer.from(content, 'utf-8').toString('base64'),
    branch,
  };
  if (sha) body.sha = sha;
  if (author) { body.author = author; body.committer = author; }
  const res = await fetch(
    `https://api.github.com/repos/${owner}/${repo}/contents/${filePath}`,
    { method: 'PUT', headers: ghHeaders(token), body: JSON.stringify(body) }
  );
  if (!res.ok) throw new Error(((await res.json()) as { message?: string }).message ?? `PUT failed: ${res.status}`);
}
```

**[VERIFIED: existing route.ts]** — The `author`/`committer` field is additive: the GitHub REST API `PUT /repos/{owner}/{repo}/contents/{path}` accepts optional `author` and `committer` objects. Adding them does not break existing behavior. [ASSUMED — standard GitHub REST API behavior; not re-verified against GitHub docs in this session, but this is well-established API design.]

### Pattern 3: CodeMirror 6 ViewPlugin Decoration (new, inline unknown-step highlight)

CodeMirror 6 (`@codemirror/view`) provides `ViewPlugin` + `Decoration.mark()` for inline text decoration. The pattern is a `ViewPlugin` that rebuilds a `DecorationSet` on each update using `RangeSetBuilder`.

```typescript
// Source: @codemirror/view 6.x — ViewPlugin pattern [ASSUMED: CM6 docs pattern]
import { ViewPlugin, Decoration, DecorationSet } from '@codemirror/view';
import { RangeSetBuilder } from '@codemirror/state';
import type { EditorView, ViewUpdate } from '@codemirror/view';

const unknownStepMark = Decoration.mark({ class: 'cm-unknown-step' });

function buildDecorations(view: EditorView, expressions: string[]): DecorationSet {
  const builder = new RangeSetBuilder<Decoration>();
  const STEP_LINE_RE = /^\s+(given|when|then|and|but)\s+(.+)/i;
  for (let i = 1; i <= view.state.doc.lines; i++) {
    const line = view.state.doc.line(i);
    const m = line.text.match(STEP_LINE_RE);
    if (!m) continue;
    const stepText = m[2].trim();
    if (!matchesCatalog(stepText, expressions)) {
      // Mark only the step text portion (after keyword + space)
      const stepStart = line.from + line.text.indexOf(m[2]);
      builder.add(stepStart, line.to, unknownStepMark);
    }
  }
  return builder.finish();
}

export function unknownStepPlugin(expressionsRef: { current: string[] }) {
  return ViewPlugin.fromClass(
    class {
      decorations: DecorationSet;
      constructor(view: EditorView) {
        this.decorations = buildDecorations(view, expressionsRef.current);
      }
      update(update: ViewUpdate) {
        if (update.docChanged || update.viewportChanged) {
          this.decorations = buildDecorations(update.view, expressionsRef.current);
        }
      }
    },
    { decorations: v => v.decorations }
  );
}
```


### Pattern 5: Catalog GET — merge proposals with official steps

`/api/catalog` GET currently reads `step-catalog.json` from FS. Extended behavior:

1. If `githubToken` + `catalogBranch` are in headers: fetch both files from GitHub API. 404 on `step-proposals.json` = empty array (not an error).
2. Merge arrays: official steps first, then proposals. Each proposal item gets a `_proposed: true` flag (or use `status: "proposed"`) so the client can render the badge.
3. Fallback: if no GitHub config or API fails, read from FS (existing behavior).

**Header pattern:** Same as `/api/github/push` — pass settings as headers from client. Client reads `settings.githubToken`, `settings.githubOwner`, `settings.githubRepo`, `settings.catalogBranch` from `useSettings` and passes them as `x-github-*` headers.

### Anti-Patterns to Avoid

- **Never write `step-proposals.json` to the local filesystem** — it lives on the `catalog` GitHub branch only. The old `/api/catalog/propose` wrote to FS; this phase replaces that path entirely.
- **Never pass token in the request body** — all GitHub tokens go in headers (`x-github-token`). Established rule T-05-03-03.
- **Never use `filePath.includes('..')` check alone** — use the full whitelist regex too (`/^[\w./-]+$/`). Established in T-05-03-01.
- **Never re-run catalog `npm run catalog`** for proposals — proposals bypass the local build script entirely, going straight to GitHub.
- **Do not recreate the `matchesCatalog` function** in the ViewPlugin — import/share with `_content.tsx`.

## Common Pitfalls

### Pitfall 1: RangeSetBuilder requires ranges in ascending order
**What goes wrong:** `RangeSetBuilder.add()` throws if ranges are not added in document order (from < previous from). Since we iterate lines 1→N this is fine, but if logic ever jumps out of order it silently corrupts decorations.
**How to avoid:** Always iterate `view.state.doc.lines` in ascending line number order. [ASSUMED: CodeMirror 6 RangeSetBuilder constraint — well-documented in CM6 migration guide]

### Pitfall 2: ViewPlugin captures stale closure values
**What goes wrong:** If `expressions` array is captured in the `ViewPlugin` class constructor closure, updates to the catalog (after first load) won't be reflected.
**How to avoid:** Use a `ref` pattern (same as `stepExpressionsRef` in GherkinEditor.tsx lines 79-81). Pass the ref object to `unknownStepPlugin(ref)` and read `ref.current` inside `buildDecorations`. [VERIFIED: GherkinEditor.tsx]

### Pitfall 3: `step-proposals.json` 404 on first use
**What goes wrong:** Before any proposal has ever been pushed, the file doesn't exist on the catalog branch. `GET /contents/step-proposals.json?ref=catalog` returns 404.
**How to avoid:** In `/api/catalog` GET handler, treat 404 on `step-proposals.json` as an empty `{ steps: [] }`. Log but do not throw. [CITED: CONTEXT.md specifics — "treat 404 as empty array"]

### Pitfall 4: GitHub PUT conflict on concurrent proposal (merge race)
**What goes wrong:** Two QA colleagues submit proposals within seconds. Both fetch the same SHA. The second PUT fails with a 409 conflict because the SHA is stale.
**How to avoid:** The route must retry once on 409: fetch the updated SHA and retry the PUT. This is the "optimistic concurrency" pattern. Alternatively, return a clear error "Another proposal was submitted simultaneously — please try again". [ASSUMED: GitHub API 409 behavior on stale SHA — standard behavior]

### Pitfall 5: `catalogBranch` field absent in old localStorage entries
**What goes wrong:** Existing users have Settings stored in `localStorage` without `catalogBranch`, `commitName`, `commitEmail`. On load, `readStorage()` merges with `DEFAULTS` — so new fields get their defaults automatically.
**How to avoid:** The existing `{ ...DEFAULTS, ...parsed }` merge in `useSettings.ts` handles this correctly. No migration needed. [VERIFIED: useSettings.ts line 34]

### Pitfall 6: `@base-ui/react` Dialog vs Radix — different import path
**What goes wrong:** Searching for `@radix-ui/react-dialog` patterns online will give wrong imports. This project uses `@base-ui/react` (v1.5.0).
**How to avoid:** Import from `@base-ui/react`. Check `@base-ui/react` docs for `Dialog`, `Dialog.Trigger`, `Dialog.Portal`, `Dialog.Backdrop`, `Dialog.Popup`. [VERIFIED: package.json — no @radix-ui packages present]

### Pitfall 7: `CatalogStep` type doesn't include `status: "proposed"`
**What goes wrong:** TypeScript will reject `status: "proposed"` because `CatalogStep.status` is typed as `'implemented' | 'wanted' | 'deprecated'`.
**How to avoid:** Extend the union in `lib/types.ts`: `status: 'implemented' | 'wanted' | 'deprecated' | 'proposed'`. [VERIFIED: lib/types.ts line 12]

### Pitfall 8: Commit preview dialog must fire before EVERY push
**What goes wrong:** D-08 requires the preview to show before feature file pushes too (not only proposals). The existing `handleCommitGitHub` in `_content.tsx` bypasses any confirmation.
**How to avoid:** Replace the direct `handleCommitGitHub` call with a pattern that shows `CommitPreviewDialog` first, then proceeds. The dialog's onConfirm callback triggers the actual push.

### New Input Validation Requirements

Three new fields in Settings flow through to API route headers. The API route MUST validate them:

| Field | Validation Rule | Risk |
|-------|----------------|------|
| `catalogBranch` | `GITHUB_NAME_RE` (same as owner/repo) | Path injection into GitHub API URL |
