## What Was Built

### Architettura finale: parser server-side + linter async

Il parser ufficiale `@cucumber/gherkin` usa `node:module` internamente e **non si bundla nel browser**. Anziché degradare al solo fallback manuale lato client, il parser gira **lato server** dove Node è disponibile, e il linter CodeMirror lo interroga via fetch.

**`web-ui/src/app/api/lint/route.ts`** (nuovo, runtime Node):
- `POST { content: string }` → istanzia `Parser(new AstBuilder(IdGenerator.uuid()), new GherkinClassicTokenMatcher())` e parsa
- Documento valido → `{ errors: [] }`
- `CompositeParserException` (o singolo `ParserException`) → mappato a `{ errors: [{ line, column, message }] }`
- try/catch globale → su richiesta malformata/errore inatteso ritorna `{ errors: [] }` (mai 500, niente spam)

**`web-ui/src/lib/gherkin-cm.ts`** (linter asincrono):
- `gherkinLinter = linter(async (view) => {...}, { delay: 600 })` — debounce 600ms per non chiamare l'API ad ogni tasto
- `fetchServerLintErrors(content)` → `await fetch('/api/lint', POST)`, mappa `errors[]` a `Diagnostic` con `from = doc.line(clampedLine).from + (column-1)`, `to = line.to`, `severity: 'error'`. In try/catch → `null` su fallimento
- `computeManualDiagnostics(doc, parserErrorLines)` — helper sincrono puro con le regole manuali (step fuori blocco, scenario vuoto, Feature mancante, keyword non capitalizzata); usato sempre come complemento e come fallback se il fetch fallisce
- Rimosso l'hack client `_nodeRequire`/`new Function` (tentava di girare il parser nel browser — non funzionava)

**`web-ui/src/components/GherkinEditor.tsx`**:
- `lintGutter()` aggiunto alle extensions dopo `gherkinLinter` → icone errore/warning nel gutter

**`web-ui/next.config.ts`**:
- `serverExternalPackages: ['@cucumber/gherkin', '@cucumber/messages']` — Next.js non tenta mai di bundlarli nel client

**Build:** `npm run build` passa pulito; `/api/lint` registrata come route dinamica (ƒ); `/editor` resta Static (1.4 kB); `npx tsc --noEmit` zero errori. Test offline del parser confermato: feature valido → `{errors:[]}`, feature rotto → errori localizzati con line/column/message.

## Deviations from Plan

### Pivot architetturale: parser server-side anziché client (Rule 4 — coordinato)

**Trovato durante:** Task 2 (verifica bundling)

**Issue:** `@cucumber/gherkin`/`@cucumber/messages` usano `node:module` e non si bundlano per il browser. Il primo approccio (parser nel client con fallback manuale) avrebbe lasciato il browser SENZA i veri errori di compilazione — contro l'obiettivo del piano (LINT-01).

**Soluzione adottata:** spostato il parser lato server (endpoint Node `/api/lint`) e reso il linter CodeMirror asincrono (fetch + debounce). Così i veri errori del parser ufficiale arrivano anche nel browser, con le regole manuali come complemento e fallback robusto.

**Impatto:** il parser ufficiale è ora effettivamente attivo nell'esperienza utente (via API). Nessuna regressione: se `/api/lint` fallisce, il linter usa solo le regole manuali e l'editor resta funzionante.
