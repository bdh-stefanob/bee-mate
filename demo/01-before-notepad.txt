--------------------------------------------------------------------------------
  OPENING  (30 seconds)
--------------------------------------------------------------------------------

SAY:
  "Thanks for the time — I want to show you something I've been building.
   It solves a real problem I see every day in the QA team.
   I'll keep it under 15 minutes."

  [Switch to THIS FILE in Notepad — point at it on screen]

  "This is what a test scenario looks like today. Written by one of our QAs
   last month. It's Notepad. No structure, no shared language."

  [Scroll slowly through the BEFORE EXAMPLE at the bottom of this file]

  "45 steps — just to place one order. Three lines just to say
   'the user confirms their phone number'. It takes 30 minutes to write,
   it's unreadable to anyone outside QA, and there's no way to reuse any of it."


KEY POINT TO LAND:
  -> Every QA writes differently. Same flow, different words. No consistency.
  -> Nobody knows if the same flow is already covered by someone else.
  -> A product owner cannot read this. The business cannot validate it.


--------------------------------------------------------------------------------
  ACT 1 — THE CATALOG  (4 minutes)
--------------------------------------------------------------------------------

  [Switch to the browser — editor page]
  [Point to the StepBrowser panel on the right]

SAY:
  "What I've built is a portal where the team writes scenarios using a
   shared catalog of approved steps. Think of it as a vocabulary that the
   whole team agrees on."

  [Click the G (Given) filter]

  "These are our Given steps — starting conditions. Standard, approved,
   reusable by anyone on the team."

  [Click the W (When) filter]

  "These are the When steps — user actions. Notice: not 'click the weight
   loss banner'. Instead: 'the user selects Weight Loss from the popular
   services menu'. One line that a product owner can read."

  [Click the T (Then) filter]

  "And these are our assertions. What we expect the system to do.
   Clear, unambiguous, agreed."

  [Reset filter to All — type "weight" in the search box]

  "Everything is searchable. I'm building a weight loss scenario — I find
   the relevant steps in seconds."


KEY POINTS TO LAND:
  -> Shared vocabulary = no more inconsistency across the team.
  -> Declarative style = readable by the business, not just QA.
  -> Searchable = fast to compose, hard to get wrong.


--------------------------------------------------------------------------------
  ACT 2 — WRITING A SCENARIO LIVE  (5 minutes)
--------------------------------------------------------------------------------

  [Click the + button to open a new editor tab]
  [Clear the search box in StepBrowser]

SAY:
  "Let me write a scenario from scratch. New patient, first-time weight
   loss order. Watch how fast this goes."

  [Type the following — slowly, let them read it]

  ---- TYPE THIS ----
  @brochure-clinic @weightloss
  Feature: Weight Loss Treatment — First Time Order

    Scenario: New patient places a Wegovy order

      Given an existing logged-in user
      When the user selects "Weight loss" from the popular services menu
      When the user selects "I'm New" as their service status
      When the user selects medicine "Wegovy" with quantity "0.25mg"
      When the user completes the medical history questionnaire
      Then the system shows the order submission confirmation
      Then the order is placed on PIMS with status "Awaiting ID approval"
  -------------------

SAY (while typing):
  "Tags at the top organise the file in the repo automatically.
   Feature title — business language.
   And now the scenario steps — I pick from the catalog, no free-typing."

  [Point at the StepBrowser — steps filter/highlight as you type]

  "No orange warning. Every step I used is already approved in the catalog."

  [Now add ONE made-up step]

  ---- ADD THIS LINE ----
      When the user dismisses the promotional banner
  -----------------------

  [Point at the orange warning banner that appears]

SAY:
  "Now I've added something that doesn't exist yet. The tool flags it
   immediately. This is the governance mechanism."

  [Click 'Propose to catalog']

  "The QA ticks it and submits for approval — it becomes 'wanted'.
   As the lead, I review it: is this the right abstraction? Is there
   already a step that covers this? I approve or suggest an alternative.
   Once approved, it's available to the whole team."


KEY POINTS TO LAND:
  -> Real-time validation — you can't silently introduce inconsistent steps.
  -> Governance loop: propose → review → approve. Steve controls the vocabulary.
  -> 45 imperative steps → 7 declarative steps. Same coverage, 10x more readable.


--------------------------------------------------------------------------------
  ACT 3 — SAVING AND THE BIGGER PICTURE  (2 minutes)
--------------------------------------------------------------------------------

  [Press Ctrl+S to save]
  [Point at the sidebar — Changes section]

SAY:
  "When I save, the scenario is written as a proper .feature file directly
   into the Git repository. No copy-paste, no manual file management.
   It appears here in the sidebar — I can see exactly what changed."

  [Pause — let it land]

  "So what does this mean in practice?
   Today: 30 minutes in Notepad, inconsistent, not reviewable, not reusable.
   With this: 3 minutes, validated, in version control, readable by the PO."


KEY POINTS TO LAND:
  -> Directly in Git = traceable, reviewable on pull request.
  -> The team's vocabulary grows over time — the catalog becomes an asset.

--------------------------------------------------------------------------------
  IF ASKED — QUICK ANSWERS
--------------------------------------------------------------------------------

  Q: How long did this take to build?
  A: "A few weeks of evenings — it's built on standard open-source tools.
      The hard part was the methodology, not the code."

  Q: Does the whole team need to use it?
  A: "No — we can adopt it gradually. Even one QA using it raises the bar
      for the whole team because the .feature files land in the same repo."

  Q: What happens to the existing Notepad test cases?
  A: "They can be imported — I can paste them in and the tool will flag
      which steps need to be added to the catalog. Migration is incremental."

  Q: Can the business / POs access this?
  A: "Yes — it's a web app, no install needed. They can read scenarios,
      they just can't edit the catalog without approval."

  Q: Is this just for web testing?
  A: "It's designed for any BDD scenario. The catalog adapts to whatever
      flows the team needs to cover."

Test Case: Weight Loss New Patient - Wegovy Order
Tester: QA
Date: June 2026
Status: PASS

PRE-CONDITIONS:
- user is logged in to the website
- user has a valid account
- website is accessible

STEPS:

1. go to homepage
2. find the "Popular Services" section on the homepage
3. click on the dropdown
4. scroll down to find "Weight Loss"
5. click "Weight Loss" - page should load
6. wait for page to load
7. there should be a button that says "Get Started Online"
8. click "Get Started Online"
9. a popup/modal appears
10. select "I'm New" (radio button on the left side)
11. click continue button (green button at the bottom)
12. medicine selection page - should show list of medicines
13. find Wegovy in the list and click on it
14. a dropdown appears for quantity - select "0.25mg"
15. click "without coaching" option
16. click next
17. confirmation page for medicine - read information
18. click the checkbox to confirm you have read it
19. click confirm button
20. important information page
21. scroll down to read all the text
22. click "I confirm" checkbox
23. click continue
24. height and weight page
25. enter height in cm field
26. enter weight in kg field
27. click calculate BMI (if button exists)
28. click next
29. medical history - lots of questions
30. answer all questions with "No"
31. click next on every page (there are like 5-6 pages)
32. order summary page - check everything looks right
33. select "Store Pickup" option
34. click place order
35. ID verification page
36. click "Upload Photo ID"
37. choose file from computer (driving licence)
38. wait for upload
39. click "Take a selfie" button
40. take selfie or upload photo
41. click submit
42. order confirmation page should appear
43. check for confirmation message
44. check that a message appears in the secure inbox
45. check PIMS (need access) - status should say "Awaiting ID approval"

NOTES:
- sometimes step 9 doesn't work on Safari, use Chrome
- step 31 might be different if user has pre-existing conditions
- PIMS check needs admin access, ask Steve

EXPECTED RESULT: Order placed successfully and visible in PIMS
ACTUAL RESULT: PASS (tested on Chrome, Windows 11)
